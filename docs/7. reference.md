# Technical Reference

This section provides the low-level specifications for the HuskHoard storage format and CLI.

## 1. The Husk Object Header (4096 bytes)
Every object on a HuskHoard volume begins with a 4KB header, aligned to the disk's physical sectors.

| Offset | Size | Field | Description |
| :--- | :--- | :--- | :--- |
| 0 | 8B | `magic_bytes` | `USTD\x00\x01\x02\x03` |
| 8 | 2B | `format_version` | Current version: 1 |
| 10 | 2B | `flags` | Operational flags (e.g., deleted, partial) |
| 12 | 1B | `compression_type` | 0=None, 1=Zstd |
| 13 | 3B | `reserved_pad` | Byte 0 doubles as `ext_blocks`: the count of extra 4KB blocks appended after the payload when TLV metadata overflows the 3960-byte `tlv_data` field. Remaining bytes are structural padding for 64-bit alignment. |
| 16 | 8B | `payload_size` | Uncompressed size in bytes |
| 24 | 8B | `compressed_size` | Compressed size in bytes |
| 32 | 8B | `padded_size` | Total size aligned to 4KB sectors |
| 40 | 16B | `object_uuid` | Unique ID for this specific version |
| 56 | 16B | `tape_uuid` | ID of the volume this object belongs to |
| 72 | 8B | `mtime` | Original POSIX modified time |
| 80 | 8B | `ctime` | Original POSIX created time |
| 88 | 4B | `posix_mode` | Original read/write/execute permissions |
| 92 | 4B | `uid` | Original POSIX User ID |
| 96 | 4B | `gid` | Original POSIX Group ID |
| 100 | 32B | `data_checksum` | BLAKE3 cryptographic hash of payload |
| 132 | 4B | `header_crc32` | CRC32 integrity check for bytes 0-131 |
| 136 | 3960B| `tlv_data` | Type-Length-Value packed variable metadata |

### TLV Metadata Packing
The `tlv_data` block stores variable-length information, packed as `[type: 2B][length: 2B][value]` entries:
*   **Type 0x01:** Original Filename.
*   **Type 0x02:** Linux Extended Attributes (xattrs).
*   **Type 0x03:** StreamGate Jump Table — the per-frame compressed size for every 16MB frame, used to reconstruct O(1) seek offsets. This is also mirrored into the `object_frames` SQL table (see The Catalog).

If the packed TLV data exceeds the 3960-byte inline capacity (common with many xattrs or a large Jump Table), the overflow spills into one or more additional 4KB "extension blocks" appended immediately after the object's payload on the volume, with the count recorded in `reserved_pad[0]` above.

## Storage Interface Specs
*   **Block Size:** 4096 bytes (Logical), 262,144 bytes (Physical SCSI Tape Frame).
*   **Tape Markers:** Uses standard SCSI `EOF` filemarks between every archived object.
*   **Reported Capacity:** `info`/`scrub` query the real drive/media capacity from physical LTO drives via the SCSI Tape Capacity log page (`sg_logs -p 0x31`) when the `sg3-utils` toolchain is available. If that lookup fails — `sg_logs` isn't installed, or the drive/media doesn't support the log page — HuskHoard falls back to a fixed 12TB (LTO-8 class) placeholder. `rclone:` remotes always report a fixed 1PB placeholder regardless of actual quota. Treat cloud fill percentages as directional, and disk/tape fill percentages as exact only when the `sg_logs` lookup succeeds.
*   **Write-Time Admission Check:** Independently of the capacity lookup above, the archiver currently uses a fixed 12TB assumption when deciding whether a *physical tape* has room for a new object, regardless of what `sg_logs` reports. On tapes smaller than 12TB, this check alone won't stop a write from being attempted past the tape's true end — don't rely on it in place of monitoring `info` output and your own rotation policy.

## 2. CLI Command Summary & Examples

| Command | Description | Example Usage |
| :--- | :--- | :--- |
| **`daemon`** | Starts the interceptor, policy engine, and HTTP Gateway. | `./huskhoard daemon` |
| **`format`** | Writes a Volume Header to LBA 0 of a drive. | `./huskhoard format --tape-dev /dev/sdb` |
| **`info`** | Displays capacity and "Wasteland" statistics. | `./huskhoard info --tape-dev /dev/sdb` |
| **`scrub`** | Verifies BLAKE3 hashes for all data on a volume. | `./huskhoard scrub --tape-dev /dev/sdb` |
| **`cat`** | Streams a file directly to stdout with zero SSD writes. | `./huskhoard cat --file-path /var/log/syslog --offset 1024 --length 500 > snippet.log` |
| **`restore`** | Manually extracts a specific version of a file. | `./huskhoard restore --file-path /home/jm/doc.pdf --dest-path ./recovered.pdf --version 1` |
| **`rm`** | Permanently deletes a file from SSD and Catalog. | `./huskhoard rm --file-path /home/jm/bad_render.mp4` |
| **`repack`** | Reclaims space by migrating active data to a new tape. | `./huskhoard repack --source-tape /dev/sdb --dest-tape /dev/sdc` |
| **`prune`** | Deletes orphaned catalog records missing from the SSD. | `./huskhoard prune` |
| **`rebuild`**| Recovers a lost database by scanning hardware. | `./huskhoard rebuild --tape-dev /dev/sdb` |
| **`export`** | Exports the SQLite catalog to Parquet format. | `./huskhoard export --format parquet --output catalog.parquet` |

## Storage Interface Specs
*   **Block Size:** 4096 bytes (Logical), 262,144 bytes (Physical SCSI Tape Frame).
*   **Tape Markers:** Uses standard SCSI `EOF` filemarks between every archived object.
*   **Reported Capacity:** `info`/`scrub` currently report a fixed 12TB for any physical LTO drive and a fixed 1PB placeholder for any `rclone:` remote, regardless of actual hardware/quota. Treat the fill percentage as directional rather than exact until hardware-specific capacity lookup ships.

## 3. Performance Tuning
*   **Alignment:** HuskHoard enforces 4096-byte alignment. This ensures compatibility with **4Kn Advanced Format** drives and prevents "Partial Sector Writes."
*   **O_DIRECT:** HuskHoard uses `O_DIRECT` to bypass the Linux Page Cache. This prevents archival tasks from "starving" your system RAM, keeping your desktop responsive while large backups occur.
*   **Zstd Window:** HuskHoard uses a sliding Zstd window optimized for 16MB frames, balancing high compression ratios with fast random-access rehydration.
*   **HTTP Stream Squelching:** The gateway detects BrokenPipe errors during seeks. This allows for rapid timeline scrubbing in VLC without spamming system logs or resource leaks.
