### Section 4: Volume Management (`volumes.md`)

# Volume Management

## 1. Physical LTO Tape Support
HuskHoard provides native support for professional LTO Tape drives.
*   **Device Path:** Use the non-rewinding character device (e.g., `/dev/nst0`).
*   **Hardware Management:** HuskHoard automatically manages tape positioning. It uses `MTREW` to rewind, `MTEOM` to find the end of data for appending, and `MTFSF` (Forward Space File) to instantly jump to specific files using hardware filemarks.
*   **SCSI Framing:** Writes are buffered into 256KB frames, the industry standard for preventing "shoe-shining" (frequent stopping/starting) and maximizing tape head life.

## 2. Hard Drives (SMR vs. CMR)
HuskHoard is **SMR-Native**. By writing data in one continuous log, it avoids the performance issues associated with Shingled Magnetic Recording.

### Sticky Drive Allocation (Sequential Fill)
When presented with multiple Primary or Replication volumes, HuskHoard does not stripe or round-robin data across them. It uses a **"Sticky" Sequential Fill** algorithm. It sorts available volumes by *most used space* first. This ensures that Volume 1 is filled completely before Volume 2 is touched, preventing your archive from becoming fragmented across multiple physical disks and ensuring cold drives can remain spun down.

## 3. Hardware Identity & Auto-Tracking
HuskHoard does not rely on fragile Linux device paths like `/dev/sdb1` that can change across reboots:
*   **Volume UUIDs:** Every formatted volume has a unique ID stored in its 4KB header (`USTDVOL`).
*   **Hard Drives (HDDs/SSDs):** Tracked by factory serial numbers pulled from `/sys/block/*/device/serial`.
*   **LTO Tape Drives:** Tracked via SCSI VPD Unit Serial Number (Page 0x80) from `/sys/class/scsi_tape/*/device`, falling back to SCSI model strings.
*   **Optical Discs:** Discs inserted into `/dev/sr0` through `/dev/sr9` are identified by inspecting LBA 0 for the volume UUID in their 4KB header.
*   **Cloud Remotes:** Tracked by a deterministic Hash-UUID generated from the `rclone` destination string.
*   **Auto-Rescan:** If an external drive moves to another port, HuskHoard rescans `/sys/block` on startup and reconciles the catalog with the new device node.

## 4. Optical Media Support (BD-R, DVD, M-DISC)
HuskHoard supports optical media as immutable, offline-capable cold storage:
*   **Burn & Ingest:** You can format an image file (`.img`), archive data into it using HuskHoard, and burn that raw image directly to optical media (BD-R, BD-RE, DVD-R, M-DISC).
*   **Read-Only Safety:** When an optical device path (`/dev/sr*` or `/dev/cdrom`) is recognized, HuskHoard automatically marks its capacity as 100% full. This ensures the Janitor will never attempt write or append operations against physical discs.
*   **Automatic I/O Compatibility:** Linux optical drivers reject `O_DIRECT`. HuskHoard detects optical devices and automatically falls back to buffered I/O, preventing `EINVAL` kernel panics.
*   **Live Rescanning:** When a new disc is inserted while the daemon or system is running, execute:
    ```bash
    ./huskhoard rescan
    ```
    This sweeps `/dev/sr0` through `/dev/sr9`, extracts the disc's volume UUID, sets `backend_type = 'optical'`, and updates the catalog so transparent reads and StreamGate can immediately read from the optical tray.

## 5. The Cold Library: Shelf Management
HuskHoard was designed with the understanding that you may have more data than you have SATA ports. It treats your archive drives like a **Tape Library**, where volumes can be "Ejected" and stored on a shelf.

### Persistent Hardware Identity
When you format a volume, HuskHoard captures two critical pieces of metadata:
1.  **Volume UUID:** A unique software identifier stored in the USTD Header.
2.  **Drive Serial Number:** The factory hardware ID (e.g., `WDC_WD140EDGZ_ZEK12345`) pulled from the disk controller.

This information is stored permanently in your `husk_catalog.db`. If you unplug a drive, the Catalog does not forget it; it simply marks it as **OFFLINE**.

### Handling Offline Recalls
If a user or application attempts to read a "Husk" file that resides on a drive currently sitting on your shelf, here's what actually happens today:

1.  **The Interceptor Pauses:** fanotify blocks the requesting process while HuskHoard attempts to restore the file.
2.  **A Restore Attempt Is Made:** HuskHoard looks up the file's replica(s) in the Catalog and tries to open each backing volume in turn.
3.  **Failure Is Logged, Not Prompted:** If a volume's `device_path` doesn't currently exist (the drive is unplugged/offline) and no replica succeeds, HuskHoard logs a generic error — `CRITICAL: All replicas for '<path>' are physically offline!` — to the terminal and system logs. There is currently no interactive "please insert Volume UUID / Drive Serial" prompt; check the logs and cross-reference the `tapes` table (Section 9) to find the UUID/serial you need.
4.  **The Process Is Unblocked Immediately:** HuskHoard only makes one restore attempt per read. If it fails, the file is re-stubbed and the blocked process is released right away — it will see the file's sparse hole (reading back as zeroes) rather than staying frozen until you reconnect the drive. Re-run whatever triggered the read once the volume is back online.
5.  **Reconnecting a Drive Requires a Daemon Restart:** Volume rescans (matching a drive's hardware serial back to its Catalog UUID, per the sections above) currently run only once, at `huskhoard daemon` startup. Plugging a drive back in while the daemon is already running is **not** picked up automatically — restart the daemon after reconnecting a volume.

> **Enterprise Sidecar note:** If you've configured `sidecar_socket_path` (Architecture, Section 4), HuskHoard sends a `WAKE_VOLUME` request to your Sidecar before every read and waits for a `READY` reply — this is the intended integration point for robotic tape libraries or custom "please load barcode X" operator prompts, rather than something HuskHoard prompts for natively.
### Ejecting Drives Safely
Because HuskHoard uses `O_DIRECT` and performs sequential writes, it is very "safe" for removable media. To eject a drive:
1. Ensure the **Archive Worker** is idle (check logs).
2. Use standard Linux eject commands: `sudo eject /dev/sdX`.
3. HuskHoard will continue to show the files in your `hot_tier`, preserving your ability to browse your library even when the "tapes" are offline.
